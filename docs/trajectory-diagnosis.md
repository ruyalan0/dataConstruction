# 200 步轨迹诊断：为什么尚未成功

日期：2026-09-11。分析代码基点：7ba7ab3；分支：analysis/trajectory-failures。

目前没有成功的共同背景是：视觉判断尚未可靠地转化为抓取、保持和精确放置；动作与结束判断的预算分配也有问题。但五个任务的直接瓶颈不同。align 提前停止物体修正最明显，stack/cover 尚未走完任务，coin 抓到后掉落，egg 则同时存在空抓和明显动作跟踪偏差。API 故障解释此前的中断，不能解释恢复后仍未完成。

## 1. 分析范围与结论边界

读取五条主回合的 episode-result.json、events.jsonl、原始三相机 RGB，并对照当前本地 RoboDojo 任务和奖励源码；另检查一条附加 egg 回合及原始中断轨迹。只做离线检查，没有新增 API 请求、GPU 仿真或策略修复。

所有主回合累计 200 个原生环境步，不设 API 调用上限。只有 align 是官方结束且 task_success=false；其余为开发预算截断、task_success=null，应称“截至截断尚未完成”，不能作为四个正式失败成绩。

本文 F 表示存档观测序号。恢复时多存一次观测，恢复后的 F 比累计原生步数大 1；恢复不增加总预算。API 响应次数包含 recall，恢复回合统计包含旧响应。

奖励依据为外部目录 ../RoboDojo 当前工作树：其基点为 8f2ad9de613e841a33e23d96b5385b15e9d5fa3c，存在本地修改。这里解释实际使用的本地实现，不宣称已验证最新官方协议或可提交榜单。

诊断中的“确认”指日志、源码或图像可直接支持；“疑似”需要受控仿真验证。没有存档物体真值、接触力或完整奖励子谓词，无法从透视图精确反算方块角度或确定所有碰撞/滑脱原因。已用捕获的 align 终止结果复核失败信号；本轮不是已修复后的回归验收。

### align：没有完成对齐，却已经开始“收工”

- F0–15 连续调整到近似俯抓姿态；F41 才首次闭爪抓尺，F47–50 试提未建立可靠抓取；约 F80 才进入推方块阶段。
- F95 的决策明确说右块仍旋转约 15–20°，这是模型的视觉估计，不是世界坐标测量。F98 转而描述近似对齐并释放。此后 102/200 个原生动作不再修正方块。
- F174 原文："the right block retains slight yaw, so exact face alignment is unconfirmed"，同一决策却写 "Maintain position; no further manipulation." F185 又写 "Manipulation complete; hold position." 这是直接可见的判断冲突，而非分析者猜测模型忘了什么。
- 全回合有 29 个纯保持步；F195 还用 3 步修正双臂约 0.4 mm 的漂移。最终相对初始观测，左臂误差 0.161 mm / 0.223°，右臂 0.109 mm / 0.194°。
- 当前奖励实现要求三块中心到 XY 拟合直线的最大距离不超过 8 mm，且各块至少一个轴与直线夹角小于 8°（或距 180° 小于 8°）。回原点默认容差却是逐坐标 150 mm、朝向 20°，远宽于模型追求的精度。以初始观测作原点计算，F147 起所有后续观测均已进入该容差，之后还有 54 个原生步。

高置信结论：完成判定与后半程优先级存在问题。右块偏航是未成功的强候选原因，中心共线误差也不能排除；没有奖励子条件结果，不能断言只差某个精确角度。初始观测与奖励内部原点未直接逐项对照，因此上述回位比较是基于已公开观测的代理核验。

### stack：第二次才抓稳，刚堆完两块就没步数了

初始朝向调整约 36 步，F63 才闭爪。F67 提升后曾判断保持成功，但 F83–85 已识别方块脱离。F120 附近重新对准并更深抓取，F128 才有较可信的保持证据。之后分轴、每次最多 30 mm 搬运，夹杂多次回查。

原轨迹在 162 步超时；恢复后 F174 松爪，F178 提离，F182 视觉确认两块堆叠，进展 15 与源码的两块堆叠里程碑相符。随后开始第三块，截断时仍在接近，尚未完成抓取。

这不是末端普遍不听指令：49 个完整反馈段中 47 个达到 2 mm / 2° 容差。主要损失在抓取返工、动作拆分和视觉确认。200 步只有任务原生上限 550 的 36%；加预算可能让它继续，但不能据此保证最终堆叠成功。

### cover：不是颜色记忆丢失，也不能用零分判定完全没进展

轨迹始终保留红在左、蓝在中、绿在右，并记得揭杯顺序红→绿→蓝。F60 首次闭爪，F64 提杯；F82–98 多次出现杯子倾斜、红块露出，放置位置需要修正。101 步中断恢复后继续调整；F123 做横向修正，F129 红块被遮盖，F132 松爪，F138 提离后视觉支持首杯已盖上。随后才开始中杯，F175 闭爪，200 步仍在下放。

当前奖励有六个顺序阶段，进展分值为 [0,0,5,15,30,100]。前两个覆盖阶段都记 0，因此本次 0 分不能反推出“连第一杯都没完成”。同时奖励还检查杯子倒扣轴方向（10°容差），视觉遮挡并不能独立证明该阶段所有谓词已通过。

63/63 个完整反馈段均到位，故普遍控制跟踪故障不符合此回合证据。更像是杯口/目标相对定位和放置确认慢，200 步仅为原生 800 步上限的 25%。

### coin：先抓取几何不对，取出后又在转腕时掉落

前约 55 步用于朝向与接近，F64 首次闭爪；F84 判断未提取，F100 再试，F109 仍未成功。F119/128 记录硬币比闭爪后的残余间隙窄，随后改变抓取位置，尝试夹边缘。

F191 发出 15° 转腕纠正硬币倾斜，F194 硬币明显改变在指尖的位置，F197 已脱离夹爪；此时尚未插入槽。原图可确认脱离发生在这段调整后，但不能仅凭图像区分接触摩擦不足、夹持不稳、扫掠碰撞或加速度影响。

### egg：空抓之外，实际动作也明显偏离目标

主回合三次闭爪分别在 F110、F135、F175 附近，后续 F120、F145、F187 的头部/腕部图仍显示蛋在篮中，蛋盒为空。模型多次依据画面调整，但没有建立一次可持续搬运的抓取。

34 个完整反馈段有 12 个未达 2 mm / 2° 容差，最大位置误差 22.74 mm，最大朝向误差 5.31°。附加 egg 回合更明显，31 段中 23 段未到位。早期旋转伴随非预期高度变化，下降时也出现请求 30 mm 而仅实现约 18.7 mm，以及姿态松弛。具体是 IK、可达边界、碰撞还是控制器问题，现有存档不足以定论。

执行器只有大于 60 mm 或 30° 才中断，因此几十毫米以内的持续偏差可以不触发中断。本轮没有丢失反馈，但策略缺少对持续未到位的有效处理，继续在不可靠的几何假设上试抓。不能把 egg 与 cover 一起归因于同一种纯视觉问题。

“完整反馈段”仅统计已闭合段，不把预算截断的末段当完整段；未到位以两臂共同满足 2 mm / 2° 为准。动作类型按该原生步活动操作归类，是时间成本划分，不是分别对两臂相加的次数。末端到位不证明接触、夹持或任务成功。

### A. 环境步预算没有显式进入模型上下文：已确认

agent.py 提供 frame、poses、initial_poses、feedback 和 available_frames，却没有 max_environment_steps、used_environment_steps 或 remaining_environment_steps。提示只说动作消耗官方预算；feedback.remaining_steps 是当前动作段的剩余重复次数，不是回合剩余预算。

模型无法从契约得知本次人为 200 步截断，更无法处理恢复后的帧号偏移。这与持续细调和尾段仍开始新阶段相容，但单独补字段能提高多少成功率仍需对照。

### B. 历史窗口并未固定保留当前三视图：已确认并用实际序列重放

visual_context.trim_images 只保留全会话最后 6 个图像项，recall 不重新附加当前三视图。使用 stack 已发生的 response 顺序，调用同一裁剪函数重放：

- F167 连续回查 4 次后，当前头部图被淘汰；随后 act 的 note 仍引用 F167 头部判断，此时只能依靠先前文本记忆。
- F171 连续回查 4 次后当前头部图被淘汰；第 5 次特地回查当前头部图，第 6 次后最初附带的三视图均已被淘汰，此时还保留回查得到的当前头部图；第 7 次又回查当前右腕图。
- 最终 act 仍有 F171 当前头部和右腕像素，因此不能称这次动作完全没有当前视觉。真实问题是当前视图没有保护、反复补图，以及回查成本增大。

完整序列和图像身份见 artifacts/trajectory-analysis/recall-window-audit.json。这里重放的是真实事件顺序下的裁剪逻辑，不声称保存了每次历史 API 请求原文，也不据此证明该缺陷导致某次抓取失败。

### C. link 朝向说明还不能替代抓取几何标定：已确认信息缺口，因果待验证

现有提示已正确说明世界轴、tool 轴、wxyz、link6 旋转中心，也提醒夹爪命令不是实测宽度。但尚未提供经过验证的指尖位置、夹持中心相对 link6 偏移、闭合区域或图像局部运动关系。轨迹大量时间花在近似竖直、对齐到指尖像素位置、试抓后再判断。

recall 返回图像与帧/相机标签，没有把该帧位姿一起配对返回；旧位姿可能仍在长文本中。移动腕相机的历史像素不宜直接当作同一几何参考，stack 自己也多次指出透视变化。朝向说明有帮助不等于抓取几何已经解决。

### D. 图像受控，但文本成本继续上涨：已确认成本，未证实质量下降

coin 第 73 次请求输入 73,760 token，累计输入 2,863,231；align 累计 3,021,559。stack 的 24 次 recall 不直接消耗环境步，却占了 74 个响应中的约三分之一，也重复发送长文本。不能将 token 增长直接认定为失败原因，但其成本和冗余值得单独优化。

### E. API 与恢复的责任边界

align 原先 111 步 HTTP500、stack 162 步超时、cover 101 步 HTTP500，均已恢复至 200 步；新版真实 HTTP500 重试后也继续完成。它们解释之前为什么停住，不能代替本次物理任务诊断。

恢复时逐步末端差值为 0，但并未核对物体真值；历史会话由旧事件重建，并非精确请求恢复。恢复可能影响记忆，不能完全排除。不过抓取失误在恢复前已有，未恢复的 coin/egg 也失败，因此“都因为恢复丢记忆”不符合现有证据。

## 4. 仅修改通用 harness 的修复范围（按用户最新约束修订）

### 模型信息边界：禁止直接或间接提供特权信息

最新执行修正：harness 不再设置 200 步上限，使用 RoboDojo 原生终止。本文前面 200 步为历史轨迹分析，不能作为新运行配置。模型仅接收自身已执行步数，不接收总/剩余内部时限。

用户再次明确：不能给模型特权信息。模型可见输入仅来自正式提供的任务指令、允许的相机 RGB、机器人自身末端位姿与夹爪命令回显，以及自身动作/会话记录。历史回查、摘要、恢复消息和通用提示同样受此边界约束，不能通过文字转述、工具返回或开发示例绕过。

允许的派生量必须能仅从上述信息复算，例如自身四元数导出的 link6 三轴、初始观测位姿、目标与实测末端的误差、实际位移和自身执行计数。它们不能被提升为“已接触”“已抓稳”“物体已对齐”等未经视觉验证的事实。

禁止传入对象真值位姿/速度、分割标签、未授权深度或相机标定、碰撞/接触真值、仿真内部 IK 状态、奖励/进展分数、成功标志、隐藏阶段、内部任务时限，以及从奖励源码反推的阈值、完成条件或任务专属解法。本文提到的 8°、150 mm、阶段分值等仅保留在离线分析报告，不进入策略输入或提示模板。

自身动作计数可以提供；不读取或透传内部 step_lim，不将奖励触发情况或隐藏阶段转换为剩余预算或进度反馈。

当前代码核查：observation_adapter.adapt 与进程传输按字段提取 RGB、指令、自身状态；Agent 输入由这些字段和自身执行反馈组成；recall 返回允许的历史原图；恢复重建来自过滤后的事件。run_episode_loop 读取的成功与进展分数仅写入评测结果，当前没有传回 Agent 的代码路径。该检查不等于对任意输入源的全面认证：适配器信任上游 vision 中的相机集合和正式 instruction，后续扩展仍须核验来源，不能混入新增特权视图或指令。已有观察过滤与传输等 15 项相关测试通过，未发现本次检查范围内的显式奖励/物体真值透传。

用户明确：只能修改 harness。沿用原计划的职责边界：“Astra 负责怎样完成任务，本地程序负责准确执行已选动作，以及如实报告发生了什么。”上面的任务诊断解释现象，不构成写入任务专属解法的授权。

采用原生环境终止、无 API 上限、900 秒超时和瞬态重试。修改限于本项目通用观测组织、会话与记忆、动作解释/队列、执行反馈和记录机制；保持官方观测与 EE 动作接口。模型、模拟器、物理参数、任务定义、奖励实现、底层 IK/控制器均不在修改范围。奖励阈值只用于离线解释，不注入策略上下文，也不由 harness 读取真值宣布成功。
