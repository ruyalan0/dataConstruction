现在astra出来了，它在具身智能方面表现出了很强的潜力，我想做套harness搭配astra给robodojo刷榜，刷到第一，你有什么想法。就按robodojo总榜的配置来，我有azure astra的api（/workspace/APIs/Azure-gpt-astra.py），我想做的就是类似kaiming he在arc-agi-3上做的事情。

**我建议以 Show-Harness 为动作接口基础，以 VISTA 为视觉记忆基础，再按需加入 PIVOT 式视觉选点与动作候选。先做一个“小而完整”的 Astra 机器人代理，而不是搭一套复杂的多代理系统。**

调研后，我认为最值得押注的核心是：

> **让 Astra 清楚地知道每个动作会怎样驱动机器人，能够核对动作实际产生的结果，并根据不确定性决定下一步动多远、多久之后再看。**

下面先讲相关工作的取舍，再给出可以直接进入开发的框架。这里的框架是设计方案，尚未经过 Astra × RoboDojo 实测。

## 一、相关工作中，哪些东西真正值得搬过来？

### 1. Show-Harness：最接近我们要做的基础系统

Show-Harness 将方向移动、旋转、夹爪开合等语义动作，通过本体专用解释器转换为小幅机器人运动，VLM 仍然负责细粒度操作决策。其主实验包含十个真实抓放任务，零样本模式平均成功率为 **89%**，但这不能直接外推到 RoboDojo 全任务。([arXiv][1])

我最关注两个消融结果：

| 论文中的结果                                                       | 对我们的启发                                |
| ------------------------------------------------------------ | ------------------------------------- |
| 在对应的五任务消融中，自适应动作分段达到 **96%**，始终批量执行动作降到 **74%**              | 要减少不必要的模型调用，但不能在接触附近长时间不看反馈           |
| 在一个 20 次试验的动作表示实验中，任意符号配明确动作说明达到 **95%**；语义名称不配明确说明为 **90%** | **清楚说明动作如何落到物理运动，比动作名字听起来像人话更值得优先做好** |

这些是小规模受控实验，不足以证明所有任务都遵循同样规律，但足以指导我们第一轮实现。([arXiv][2])

因此，我会给 Astra 一份稳定的 **ARX X5 本体操作说明**：坐标轴、运动方向、旋转约定、步长、左右臂对应关系，以及实际执行的反馈格式。没有必要让它在每个 episode 里重新猜这些规则。

### 2. 其他工作的取舍

| 工作                                               | 值得借鉴的机制                     | 在我们系统中的位置                                                    |
| ------------------------------------------------ | --------------------------- | ------------------------------------------------------------ |
| **VISTA**                                        | 原始视觉输入、自由推理、可回查的无损视觉记忆      | 保留收到的原图，支持回看、裁剪和比较；不要让文本摘要替代证据。([VISTA][3])                  |
| **PIVOT**                                        | 将候选位置或动作画到图像上，让 VLM 选择并逐步细化 | 用于空间判断困难时的可选工具，减少直接猜连续坐标。([Pivot Prompt][4])                 |
| **CaP-X**                                        | 通过代码组合控制与感知工具，多轮视觉反馈和技能改进   | 提供受限 Python 工作区；第一版不搬完整技能库和整套感知依赖。([GitHub][5])              |
| **Playful Agentic Robot Learning／RATs**          | 在自主交互中积累可复用程序技能，测试时冻结技能库    | 用于开发阶段自动分析失败、改进工具；与正式评测阶段分开。([arXiv][6])                     |
| **What Matters in Orchestrating Robot Policies** | 系统研究执行时长、子任务切换、观测和记忆        | 提醒我们测清这些接口因素；其部分强配置使用特权接触信息，不能直接作为 RGB-only 的证据。([arXiv][7]) |

尤其要注意，最后一项研究中，增加历史长度或 episode 内摘要并未稳定带来收益。因此，**“能访问历史”与“每次强行塞入大量历史”应当分开**。([arXiv][7])

## 二、推荐框架：一个 Astra 决策主体，四个核心模块

我建议暂称它为 **Dojo-Astra Harness**。第一版结构如下：

```text
              RoboDojo 官方观测
           RGB + 允许的机器人自身状态
                       │
                       ▼
        观测整理、原始档案、动作前后对照
                       │
                       ▼
              Astra 连续交互会话
        理解任务、决定动作、检查结果、修订计划
            │                       │
            │                       └─ 按需回看 / 裁剪 / 计算
            ▼
       左右臂联合动作指令
       方向、旋转、幅度、夹爪、执行长度
            │
            ▼
   ARX X5 动作解释器 + 可中断动作队列
            │
            ▼
       官方 EE 控制接口
            │
            ▼
       环境返回下一次正式观测
            │
            └──── 实际动作结果与图像反馈 ────┘
```

**Astra 负责“怎样完成任务”，本地程序负责“准确执行已选动作，以及如实报告发生了什么”。**

主循环只需要一个 Astra 会话。第一版不设置独立的规划代理、动作代理、批评代理，也不让左右臂各自运行一个互不知情的代理。

### 模块 A：观测与视觉记忆

每次默认给 Astra：

**当前官方相机图像、机器人自身状态、上一个动作及实际结果、必要的动作前后图像。**

其余历史按需读取。原始档案记录图像、相机名称、观测编号和动作编号；模型笔记记录目标、假设与已确认进度。

例如：

```text
当前子目标：将黄色物体放入篮子

已确认：
  红色物体已经放入篮子，证据为 frame_084 和 frame_087。

尚未确认：
  黄色物体可能在左夹爪中，但当前视角存在遮挡。

下一项检查：
  小幅抬升，观察黄色物体是否随夹爪移动。
```

这里不要求 Astra 把所有推理都填进固定表格。**固定的是证据索引和工具调用格式，任务推理仍可自由进行。**

还有一条输入边界必须从第一天落实：官方配置页面展示的 `arx_x5` 默认设置关闭了深度、相机内参和外参。实际开发应审计策略收到的观测包，不能因为仿真器内部存在这些数据，就默认把它们送给模型。([Robodojo Benchmark][8])

因此，第一版不依赖物体真值位姿、碰撞网格、实例分割真值或接触真值。任务对相机的官方覆盖配置也完整保留。

### 模块 B：可解释、可校准的动作接口

我建议让 Astra 使用以下动作概念：

```text
平移：某只手，沿明确坐标系的某个方向，移动指定幅度
旋转：某只手，绕明确坐标系的某个轴，旋转指定角度
夹爪：打开、闭合或保持
双臂：同一条指令联合指定左右臂动作
执行：短段执行，或执行到预定检查点
```

接口示意：

```python
act(
    left={
        "operation": "translate",
        "frame": "base",
        "axis": "+z",
        "distance_mm": 10,
        "gripper": "hold",
    },
    right={"operation": "hold"},
    execution="short",
)
```

这不是完整实现，而是模型与执行器之间的合同。第一版可以提供离散步长档位，避免模型每一步生成任意小数；具体档位通过 ARX X5 实测确定。

**需要分清三个量：运动幅度、执行多少个官方控制步、调用几次 Astra。**例如，移动 10 毫米可能需要多个控制步，但不一定每个控制步都调用模型。

同时支持 base 坐标系和 tool 坐标系：前者便于桌面移动，后者便于沿工具自身轴向接近。所有方向都明示，避免“向左”在头部相机、腕部相机和机器人基座之间不断改变含义。

#### 这里有一个已经核实的移植风险

Show-Harness 的真实机器人接口说明使用：

```text
[x, y, z, qx, qy, qz, qw]
```

XPolicyLab 示例 EE 动作使用：

```text
[x, y, z, qw, qx, qy, qz]
```

两者四元数顺序不同，不能原样连接。([GitHub][9])

除此之外，解释器测试还必须覆盖米与毫米、TCP 与法兰、左右臂、旋转轴、夹爪开合方向，以及未动作手臂的保持行为。**不活动的手臂必须保持有效目标，不能填一串零。**

### 模块 C：执行结果反馈与可中断队列

这是我会投入最多工程精力的模块。

执行器返回的应该是：

```text
请求：左手沿基座 +z 移动 10 mm
实际：左手移动了 7.8 mm
执行：消耗了 n 个官方控制步
状态：尚未到达目标
原因：当前观测不足以判断
证据：执行前后图像及机器人状态
```

不能把“指令已经发出”报告成“动作已经完成”，也不能仅凭没有移动就虚构“发生了接触”。

后续动作应依据实际位姿和当前未完成目标生成，避免机器人尚未到位，内部目标却不断向前累积。

**长动作段也必须能够在原生控制边界上停止。**我检查了 XPolicyLab 示例部署循环：它会在动作列表内部更新观测，但通常要执行完整个返回列表，才再次调用 `get_action()`。直接返回一长串动作，会限制模型中途重新决策的机会。([GitHub][10])

建议把动作队列放在 policy 内部，每次只向官方部署循环返回一条原生动作：

```python
def update_obs(obs):
    archive.append(obs)
    executor.observe(obs)

def get_action():
    if executor.needs_new_decision():
        decision = astra.decide(build_context())
        executor.load(decision)

    return [executor.next_native_action()]
```

这是控制结构示意。其意义是：**每个官方动作边界都能检查队列，但只有需要重新决策时才请求 Astra。**

本地检查可以包含跟踪误差过大、观测异常、动作预算耗尽，以及已建立的视觉跟踪失效。第一版不承诺本地程序能准确检测所有语义失败。

### 模块 D：带证据的完成检查与恢复

Show-Harness 的恢复代码提供了一个有用起点，但不能照搬：其公开插件主要根据测得的夹爪宽度判断空抓等状态。([GitHub][11])

对于我们的任务，夹爪宽度只能作为证据之一。薄物体可能让夹爪接近闭合，夹爪被卡住也可能留下间隙。

因此，我建议使用三个状态：

**已确认完成、已确认失败、证据不足。**

抓取后的检查可以是：物体是否随夹爪抬升，原位置是否仍有目标，多视角是否支持同一判断。放置后的检查可以是：物体是否已释放，位置是否满足当前子目标，机器人移开后是否仍保持。

这类检查仍由 Astra 根据允许观测完成。必要时执行一次小幅试抬或退让，以获得更有判别力的证据；这些动作全部消耗正常任务预算。

恢复只改变当前计划和后续动作，**不回滚仿真世界，不重置物体，也不读取官方成功判定来告诉模型答案**。最终成绩始终由官方评测器计算。

## 三、空间落地困难时，再加 PIVOT 式工具

我不建议第一版就做完整三维重建。不过，当出现“目标理解正确，但手总是去错地方”的稳定失败模式时，需要比单纯文字描述更直接的空间接口。

PIVOT 的可借鉴之处是：把候选位置或动作可视化，让模型选择，再逐步细化。([Pivot Prompt][4])

在我们的框架里，它可以分两级。

### 第一级：图像中的目标标记

Astra 先在原图中标记需要接近的区域，例如管口、杯柄、物体可夹持部位。之后的局部操作始终可以回看这个视觉目标。

这不要求得到完美三维坐标，也不能把一个二维点直接当成六自由度抓取位姿。

### 第二级：局部动作候选

只有在拥有可靠投影关系或局部运动估计时，才把若干候选动作画成箭头或候选终点，让 Astra 选择。

没有官方相机标定时，可以研究通过允许的 RGB、自身运动和视觉跟踪，估计局部关系：

$$
\Delta \text{图像特征}
\approx
J_{\text{local}}\,
\Delta \text{末端运动}.
$$

这类不依赖完整手眼标定的视觉伺服已有研究基础，但其具体适用条件和自由度有限，不能直接保证覆盖 RoboDojo 全任务。([arXiv][12])

**我把它列为第二阶段工具，不作为启动依赖。**估计不可靠、目标被遮挡或相机运动导致关系失效时，应关闭候选投影，回退到短动作与直接视觉反馈。

这里值得验证的假设是：

> 对 Astra 来说，比较几个有明确物理含义的局部候选，可能比从 RGB 直接回归准确位姿更可靠。

但这需要我们自己的消融，不能从 PIVOT 的结果直接推出。

## 四、代码如何落地：接 XPolicyLab，不重写 RoboDojo

### 1. 保留官方环境与控制链

以 XPolicyLab policy adapter 为接入点，沿用官方 `arx_x5`、`ee` 动作模式、任务覆盖配置和评测脚本。XPolicyLab 已有观测更新、动作返回、reset 和批量部署接口。([GitHub][13])

建议代码分成以下几个独立部分：

| 模块                       | 责任                        |
| ------------------------ | ------------------------- |
| `azure_session.py`       | Azure 会话、工具调用、响应状态保存和能力探测 |
| `observation_adapter.py` | 观测字段白名单、图像与状态整理、时间和编号     |
| `arx_x5_interpreter.py`  | 动作单位、坐标系、四元数、左右臂和夹爪转换     |
| `executor.py`            | 原生动作队列、实际执行反馈、限幅和中断       |
| `trace_store.py`         | 原图、动作、证据索引和 episode 内笔记   |
| `agent.py`               | Astra 交互循环与工具路由           |
| `evaluation.py`          | 官方评测调用、失败分类、成本与回归比较       |

Show-Harness 的动作解释器和插件结构值得复用，但其现有本体标定不能直接视为 ARX X5 标定。([GitHub][9])

### 2. Azure 会话保持是功能测试项

Azure Responses API 文档已列出 Astra 支持，并提供多轮响应关联机制。具体部署对推理状态延续、工具调用和上下文管理的支持仍应实际探测。([Microsoft Learn][14])

实现上，不要每轮只保存 `output_text`，然后把它拼回一个新请求。应按实际支持的协议保留响应项目、工具调用关系和会话状态。

另外，每个 episode 必须有独立会话、记忆和动作队列。API 重试不能导致机器人重复执行；旧 episode 的迟到响应也不能进入新 episode。

第一版我倾向于**每个环境进程独立运行策略状态，在模型请求层做并发调度**，先避免复杂批处理引入状态串线。

### 3. 代码工作区保持可选和受限

Astra 可以通过 Python 对已收到的图像进行裁剪、跟踪、数值计算，也可以保存笔记或生成短程序。

但工作区不应获得评测进程的任意对象访问权。否则，“让模型写代码”很容易变成读取布局文件、物体真值或成功函数。

所有真正驱动机器人的操作仍走 `act()`；代码工具本身不能偷偷调用额外仿真步、复制世界试动作或修改物理参数。

## 五、开发阶段可以自主改进，但正式评测必须冻结

RATs 展示了一条很适合你资源条件的路线：在自主交互中发现问题、形成程序技能，再以冻结技能库评测下游任务。([arXiv][6])

我们可以据此建立开发循环：

```text
跑开发任务
    ↓
整理失败录像、动作轨迹、接口返回值
    ↓
Astra 分析失败并提出修改
    ↓
自动测试与独立验证
    ↓
通过后进入下一版 harness
```

我会优先允许它修改通用机制，例如步长选择、重复失败的检测、图像组织方式、动作结果描述和通用恢复程序。

任务专用技能需要单独管理。比如，为某个具体插入任务写好完整控制脚本，可能有助于冲榜，但它与“通用模型通过统一接口直接控制机器人”的实验问题不同。

因此建议保留两个清晰的版本：

**通用 harness 版**：不使用任务专项示范或解法，主要衡量 Astra 与通用接口。

**开发经验增强版**：允许从规定的开发数据中积累并冻结通用或任务族程序，明确记录经验来源。

“不更新模型参数”不等于“没有学习任务经验”。这两个版本都可以有价值，但成绩和结论应分开报告。

## 六、我会怎样安排第一轮实验？

### 第一关：先证明这个控制界面本身可用

借鉴 Show-Harness 的人机共用接口设计，我们应提供一个最小键盘或按钮界面，让人在**相同观测、相同动作接口、相同控制预算**下操作机器人。其 GUMI 已展示了人和模型使用同一语义动作空间的方式。([GitHub][15])

这是一个很有用的开发诊断：

**人也做不出来，先查接口、观测和控制能力；人能做出来而 Astra 做不出来，再分析模型决策。**

人工操作只用于独立开发实验，不进入正式自主评测。

### 第二关：建立能区分贡献的基线

建议依次比较：

| 版本 | 配置                           | 主要问题                 |
| -- | ---------------------------- | -------------------- |
| A  | Astra 直接输出连续末端增量，正确会话延续，基础反馈 | 不加复杂 harness 时能做到什么？ |
| B  | A 改为明确语义动作、校准步长和本体说明         | 动作表示与标定是否有效？         |
| C  | B 加视觉回查、动作前后证据与完成检查          | 记忆和验证是否改善长程与恢复？      |
| D  | C 加自适应执行长度和可中断队列             | 能否减少调用而不损害成功率？       |
| E  | D 按需使用视觉目标标记、候选动作或局部伺服       | 剩余瓶颈是否主要来自空间落地？      |

先做逐项增加，再对胜出配置做关键模块移除。所有版本保持相同允许观测、环境步数上限和模型设置；同时报告调用量，避免把更多推理预算误认为某个模块本身的收益。

### 第三关：尽早覆盖全任务，不只挑成功视频

我建议先在五个维度中各选代表任务调通，再对全部配置做少量覆盖性试跑，寻找完全不适配的任务类型。之后使用独立布局验证，最后才运行完整协议。

官方当前完整入口包括 **42 个基础任务与 12 个泛化随机化配置，共 54 个可运行配置**。使用 native 次数，每个 seed 为 2,100 个 episode，三个 seed 合计 **6,300 个 episode**。([Robodojo Benchmark][16])

完整运行前要测清平均调用量。比如每个 episode 平均 50 次请求，就意味着约 31.5 万次请求；这只是预算示例，不是当前系统的实测需求。

### 第四关：评测不只看一个成功率

RoboDojo 同时报告成功率和体现部分进度的 score，总体结果按五个能力维度平均，而非直接平均全部任务。我们应直接使用官方汇总口径。([arXiv][17])

此外，开发报告至少记录：

**空间定位错误、动作执行偏差、错误宣布完成、恢复失败、预算耗尽，以及 API／接口故障。**

调用次数、延迟分布和实际环境步数也一起记录。保持官方时间推进语义，不通过额外暂停、重置或延长任务来改善结果；正式运行中的故障不能静默剔除。

闭源 API 是否能进入官方 verified 榜仍需单独确认：现行论文要求完整评测产物及 checkpoint 等材料，并进行隐藏布局验证，不能默认公开 harness 就自动满足要求。([arXiv][17])

---

## 最终建议

**第一版只做：明确动作语义、正确本体转换、短段可中断执行、动作前后视觉证据、可回查记忆。**

PIVOT 式空间工具和自主代码技能都保留为可插拔增强项，依据失败分布决定是否加入。暂时不把完整三维重建、多代理协作、专项 VLA 或 RL 训练放进启动路径。

调研后，我认为最有潜力的地方并非单独增加一个规划器，而是把下面三个问题一起做好：

> **此刻看到了什么？选出的动作实际做到了什么？在下一次必须观察之前，最多还能执行多少动作？**

这套框架既保留了 VISTA 想验证的通用模型能力，也有 Show-Harness 提供的具体控制基础。**先证明 Astra 能通过这一统一接口稳定完成跨任务闭环，再让实验告诉我们：冲榜缺的是视觉落地、接触控制，还是长程决策。**
