# 可行性评估

方案可行，已经实现为独立版本。5 秒图像序列补充两个决策点之间的可见运动，有助于判断物体是否随手移动、是否中途滑动，以及双臂是否互相遮挡；上一决策点与当前的精确状态仍保留，memory 继续概括更早阶段的信息。是否提高任务成功率，需要本版本新的抓取回合验证。

## 参考数据

已逐行核对用户提供的 `4fps_val.jsonl`：共 4,444 条、35 种任务文本、260,121 次图像引用。每条均为 system/user/assistant 三条消息；35 条只有当前观测，4,409 条含上一决策点。图像按时序排列，历史范围为 -5,000..0ms；每个时刻三路图，最多 22 个时刻、66 张图片。只有上一决策点与当前时刻附带 State，历史中间帧不带状态。

结构核对结果见 [audit/4fps-reference.json](audit/4fps-reference.json)，原始参考样例见 [首轮](examples/reference-first.json)及[完整窗口](examples/reference-full-window.json)。图片路径指向另一台机器的 `/share/workspace/...`，本机未找到抽查图片；本次验证限于 JSONL 文本结构，未据此验证参考图像内容或物理正确性。

## 与现有版本的对应

本实现采用相同的输入信息组成，保留当前项目的结构化 JSON、完整测量精度和 control_arms 输出协议。未直接使用参考文件的文本格式或 arms 包装作为运行协议，因此参考文件不能未经输出协议对齐就原样替换当前执行器。

| 情况 | 处理 |
|---|---|
| 动作持续多个采样周期 | 执行途中逐次采样，保留中间真实 RGB |
| 250ms 不是 4ms 的整数倍 | 交替使用 63/62 个控制周期；记录真实时刻，误差不累积 |
| 运行不足 5 秒 | 只取已有采样，不补帧、不复制旧图填充 |
| API 等待 | 按仿真时间计算，不采集重复静止帧 |
| 两端点与采样时刻相同 | 合并历史/上一决策角色；保留精确的决策图片 |
| 零步拒绝 | 上一决策和当前可同时间，间隔为 0，保持两端点独立 |
| 保护提前截断 | 当前状态、实际间隔与历史按实际执行前缀计算 |
| 上一决策早于 5 秒窗口 | 显式保留上一决策点；周期 RGB 仍只来自窗口内 |
| 漏采或顺序异常 | 显式报错，不用决策图片伪造中间帧 |
| 新回合 | 新建采样器和模型会话，不复用上局历史 |

当前模型输入仍有局限：4fps 会遗漏短于采样间隔的接触或滑动，RGB 本身不提供接触力；5 秒以外的历史仍依赖 memory。完整窗口最多输入 66 张图，图像 token 和推理耗时预计高于此前 3/6 图方案，具体开销尚未实测。没有把离线结构检查转换为成功率或费用改善结论。

## 验证范围

34 项离线测试通过。测试执行真实 server_loop、client、action_control、NativeToolVision 请求组装及 Swift 导出代码，并使用原生控制队列/验证器；替换 API 和物理环境。长动作案例推进 1,406 个控制周期，验证中间 4fps 捕获、窗口裁剪、不同时间图像和 IPC 字段完整性。另覆盖完整 66 图请求、memory 更新、保护、零步拒绝及输出/输入时间戳篡改拒绝。

原有版本、脚本、发布文件及两个参考 JSONL 共 1,675 个文件进行了 SHA-256 保护；进一步复用上版本原始源码和历史日志校验。只在本新目录写入文件。新版本尚未运行真实 API/Isaac 回合；真实成功率、图像开销和训练模板适配均待实跑验证。
